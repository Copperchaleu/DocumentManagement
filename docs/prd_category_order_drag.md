# 增量 PRD：分类管理页 — 分类顺序拖拽修改

> 文档类型：增量 PRD（仅描述本次变更，不重复既有分类 CRUD 全量设计）
> 作者：产品经理 许清楚（Xu）
> 关联页面：`web/src/views/CategoriesView.vue`（分类管理）
> 技术栈：前端 Vue3 + ElementPlus + Vite；后端 FastAPI + 原生 sqlite3

## 1. 变更背景

本次在现有「分类管理」页面新增**拖拽调整分类顺序**的能力。后端 `categories` 表已存在 `sort_order` 列（默认全 0），且 `list_categories_flat()` 已按 `ORDER BY COALESCE(parent_id,0), sort_order, name` 排序——即**只要写入 `sort_order`，顺序即可生效**，前端渲染链路（树 → `flattenTree` → `orderedCategories`）会自动按新序展示。但当前无任何 API 写入该列（默认全 0，退化为按名称排序），拖拽顺序能力缺失。本次变更即补齐这条"写入"链路，并以拖拽交互暴露给用户。

补充事实（已探明）：`backend/database.py` 的 `update_category` / `create_category` **已接受 `sort_order` 入参**（database.py:427/444/489/369），`get_category_tree()` 已按 `sort_order` 排出兄弟顺序。因此本次后端几乎无新 SQL，主要为新增一个批量端点 + 模型字段 + 入参校验。

## 2. 目标用户与场景

- **目标用户**：使用本系统的文档整理者（个人知识管理者 / 团队文档管理员），希望按业务优先级、使用频率自定义分类排列。
- **典型流程**：
  1. 进入「分类管理」页；
  2. 拖动某分类行（或树节点）至目标位置（必须同为某父分类下的同级）；
  3. 拖拽过程中看到高亮、放置指示线等视觉反馈；
  4. 松手，顺序立即保存并在刷新后保持；
  5. 若误拖到跨父级/跨层级位置，被拦截并回弹 + 提示，原顺序不变。

## 3. 用户故事

- **US-1 同级重排**：As a 文档整理者, I want 把同一父分类下的子分类拖到另一个位置, so that 分类顺序符合我的整理习惯。
  - 验收：对某父分类下的两个同级分类互换/移动位置后，松手即持久化；重新进入页面顺序与拖拽结果一致。
- **US-2 子树整体移动**：As a 文档整理者, I want 拖动一个带子分类的父级时其所有下级随之一起移动, so that 层级从属关系不被破坏。
  - 验收：拖动含 N 个子分类的父级，松手后该父级及其全部子孙的相对层级与从属不变，仅父级在同级中的位置改变。
- **US-3 非法拖拽拦截**：As a 用户, I want 跨父级/跨层级的拖拽被禁止并提示, so that 我不会误把分类挪到错误的层级导致混乱。
  - 验收：跨父级（拖到别的父分类下）或跨层级（拖到成为他人子分类/他人父级）的放置目标不可放置；松手自动回弹，并弹出明确提示。
- **US-4 视觉反馈**：As a 用户, I want 拖拽全程有清晰的可放置/禁止反馈, so that 我知道能否放、会放到哪里。
  - 验收：拖拽中源项高亮/半透明；合法位置显示插入指示线；非法位置显示禁止态（红圈/禁止图标），且非合法区不响应 drop。
- **US-5 现有操作不受影响**：As a 用户, I want 拖拽排序后仍能用添加子分类/编辑/删除/打开目录, so that 排序能力是增量叠加而非替换。
  - 验收：排序操作后，现有每行操作按钮与新建分类功能均正常。

## 4. 需求池

### P0（必须）
- **同级拖拽重排**：仅允许同一 `parent_id` 下的同级分类之间调整顺序；不可跨父级、不可跨层级。
- **子树整体移动**：移动某节点时，其全部下级子分类作为整体随节点移动，层级从属关系保持。
- **非法拖拽拦截 + 提示**：对跨父级、跨层级的放置目标进行拦截，松手自动回弹，并给出明确提示（如 `只能在同一父分类下调整顺序`）。
- **明确视觉反馈**：拖拽中（源项高亮/半透明）、可放置位置（插入指示线）、禁止放置（禁止态图标）三种状态齐备。
- **后端持久化 `sort_order`**：新增 reorder 端点（或复用 `CategoryUpdate`），把新的兄弟顺序写入 `sort_order`，原子化生效。
- **保留既有操作**：添加子分类 / 编辑 / 删除 / 打开本地目录 按钮与新建分类保持不变、可用。

### P1（重要）
- **原子批量保存**：一次拖拽只产生 1 次网络请求，整组兄弟的 `sort_order` 在一次事务内写入。
- **防环/防自引用复用**：复用 `update_category` 已有防环逻辑（本次仅同级重排本不会发生，但端点需保持健壮性）。
- **失败回滚/提示**：后端校验失败（id 不存在、非同一父、列表不全）返回 4xx 并带 reason；前端捕获后回弹并提示。
- **加载与禁用态**：拖拽保存期间禁用拖拽交互，避免并发重入。

### P2（可选增强）
- **乐观更新**：拖拽后先本地更新顺序，后端成功再确认；失败回滚到原序（提升体感）。
- **键盘可达性**：支持上下键/快捷键调整选中分类顺序（无障碍）。
- **拖到末尾**：明确是否允许拖到同级列表最末尾（插入到末位）。
- **批量拖拽多选**：选中多个同级一起移动（本期范围外，记录待定）。

## 5. UI / 交互设计草案

### 5.1 视觉反馈形式
- **拖拽中**：源行/源节点变为半透明或加主色描边（如 `box-shadow` + 降低 `opacity`），表示"正在搬运"。
- **可放置位置**：在合法同级相邻行之间显示一条高亮水平插入指示线（el-tree 的 `allow-drop` + 自定义 drop 指示；el-table 自行渲染指示线）。
- **禁止放置**：鼠标悬停到非法目标时显示"禁止"光标/红圈图标，drop 不生效，松手自动回弹原位。

### 5.2 非法拖拽提示方式
- 松手于非法目标 → 行自动回弹至拖拽前位置；
- 同时 `ElMessage.warning('只能在同一父分类下、同级之间调整顺序')`；
- 若后端也拒绝（极端情况），`toastError` 展示 reason 并回弹。

### 5.3 现有按钮
- **保留**「添加子分类 / 打开本地目录 / 编辑 / 删除」四枚按钮（操作列）与右上角「新建分类」。本次仅为表格/树增加拖拽能力，不改动这些按钮的现有行为。

### 5.4 实现选型建议（倾向性，最终由架构师定）
- **倾向 A：改用 `el-tree`（推荐）**
  - 依据：`appState.categoryTree` 已是嵌套结构，`get_category_tree()` 已按 `sort_order` 排出兄弟顺序；`el-tree` 原生 `draggable` + `node-drop` 直接拿到拖拽结果，`allow-drop` 可在一步内拦截跨父级/跨层级；**子树整体移动天然成立**（节点携带整棵子树），无需自管多行。
  - 代价：需把现有多列信息（本地目录、项目数、操作按钮）改写为 `el-tree` 节点的 scoped slot 内容（`render-content` 或 `#default` 插槽），工作量中等。
- **倾向 B：保留 `el-table` + HTML5 拖拽**
  - 依据：现有多列布局零改动；用 `draggable` 属性 + `dragstart/dragover/drop` 自行实现。
  - 代价：需自行维护"仅同级"约束、放置指示线、回弹与禁止态，逻辑量更大；子树整体移动需依靠"拖拽节点即拖拽其整棵子树"的语义在扁平列表中正确处理（因 `orderedCategories` 由树派生，只要只改该节点在兄弟中的序位，子孙自然跟随，但 UI 上需避免让用户误以为能单独拖某个子孙脱离父级）。
- **结论**：在能接受把行重做成树节点插槽的前提下**优先 `el-tree`**（正确性更好、拖拽逻辑更少）；若希望保留现有表格列零改动，则采用 `el-table` 方案。两种方案都必须满足第 4 节 P0 的同级/子树/拦截/反馈约束。

## 6. 后端能力建议

### 6.1 新增批量重排端点（推荐）
```
POST /api/categories/reorder
Body: { "parent_id": int | null, "ordered_ids": [int, ...] }
```
- 语义：把 `parent_id` 下的全部兄弟，按 `ordered_ids` 给出的顺序赋 `sort_order = 索引`。
- 校验（任一不满足返回 400 + reason）：
  1. `ordered_ids` 非空且互不相同；
  2. 所有 id 均存在；
  3. 所有 id 实际 `parent_id` 与请求 `parent_id` 完全一致（根级用 `null`）；
  4. `ordered_ids` 覆盖该父级下**全部**子分类（数量一致），避免遗漏导致顺序歧义。
- 实现：在单个事务内循环复用既有 `db.update_category(id, sort_order=k)`（DB 层已支持 `sort_order` 入参，无需新增 SQL）；成功返回 `{ ok: true }` 或更新后的 tree/flat。
- 为什么不直接对每节点调 `PUT /api/categories/{id}`：批量端点原子、仅 1 次请求、校验集中、避免 N 次往返与并发竞态。

### 6.2 模型补充（建议）
- 在 `CategoryUpdate` 增加 `sort_order: Optional[int] = None`（为单节点调序与未来兼容留口，本期主路径用 reorder 端点）。
- 可选：在 `CategoryCreate` 增加 `sort_order: Optional[int] = None`，便于新建时指定插队位置（默认尾部）。

### 6.3 复用的既有能力
- `db.update_category` 已接受 `sort_order` 并写入（database.py:427/444/489）；`get_category_tree()` 已按 `sort_order` 排序返回——**本次后端几乎无新 SQL**，主要是新增一个端点 + 模型字段 + 入参校验。

## 7. 验收标准（DoD，可量化 / 可测试）
1. **同级重排生效**：在任意父级下拖动子分类到新位置，松手后前端顺序更新；调用 `GET /api/categories?tree=true` 与 `flattenTree` 结果顺序与拖拽结果一致；**重启/刷新页面后顺序保持不变**（DB `sort_order` 已落库）。
2. **子树整体**：对含 ≥1 子分类的父级重排，其子孙的 `parent_id` 链与层级在 DB 中不变，仅该父级 `sort_order` 变化。
3. **非法拦截**：构造跨父级 drop（如把 A 父下的子拖到 B 父下）与跨层级 drop（如把节点拖成他人子节点），UI 禁止放置并回弹；`POST /api/categories/reorder` 传入跨父级 `ordered_ids` 返回 400。
4. **视觉反馈**：拖拽中源项高亮/半透明；合法位置有插入指示线；非法位置显禁止态；三者均可在 UI 复现。
5. **请求数**：一次同级重排仅触发 1 次后端请求；后端在 1 个事务内完成整组写入。
6. **现有功能回归**：添加子分类 / 编辑 / 删除 / 打开目录 / 新建分类 在排序后均可正常使用，且不受排序影响。
7. **校验**：`ordered_ids` 缺失/重复/非同父/未全覆盖兄弟时，端点返回 4xx + 明确 reason，且不改变任何 `sort_order`。

## 8. 待确认问题（Open Questions）
1. **末尾放置**：是否允许把分类拖到同级列表"最末尾"（插入到末位）？还是仅允许插在两个现有同级之间？
2. **乐观更新**：拖拽后是否采用"先本地更新、后端成功再确认、失败回滚"？还是"等后端返回再更新"？
3. **键盘可达性**：是否需要支持键盘（上下键/快捷键）调整顺序以满足无障碍？
4. **范围边界**：本期严格"仅同级重排"（跨父级/跨层级一律禁止），还是可接受把"跨父级移动"作为 P2 未来项？（确认本 PRD 范围 = 仅同级）
5. **ordered_ids 完整性**：reorder 端点要求传"该父级下全部兄弟"（推荐，避免歧义），还是允许只传受影响的部分？
6. **备份触发**：排序写入后是否需主动触发一次 DB 备份（现有有定时/手动备份），还是依赖既有自动备份即可？
7. **path 是否受影响**：`path` 列基于父级目录路径生成，同级排序不改变路径；确认排序变更无需改写任何 `path`/`path_label`。
8. **并发**：多标签页同时拖拽的覆盖风险（SQLite 单实例、并发低）；是否需要版本号/乐观锁防护？
