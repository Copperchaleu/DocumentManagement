# PRD：本地文档管理系统 — 内容存储从 Word/HTML 富文本迁移至 Markdown

> 文档角色：产品需求文档（精简版）
> 配套依据：技术评估报告 `docs/eval_markdown_migration.md`（源码实证，本文不再重复技术细节）
> 文档负责人：产品经理 许清楚（Xu）
> 适用版本：本地文档管理系统 v2（FastAPI + Vue3/ElementPlus + python-docx）

---

## 1. 背景与问题（Why）

当前系统内容**真源**为 `projects.content`（TEXT 列），存储的是 wangEditor HTML 富文本；Word（`.docx`）只是派生产物——由 `backend/word_service.py` 把同周期项目的 HTML 合并生成，存进 `period_file_versions.file_content`（BLOB）并同步本地 `data/documents/*.docx`。

现有方案的问题：
- 内容以 HTML 富文本存储，**不可 diff、难以版本化、长期可读性弱、易被厂商绑定**；
- 纯展示样式（字体/字号/颜色/对齐）是粘贴 Word 时带入的噪音，**对归档检索无价值**；
- 前端 wangEditor 体积与维护成本偏高，与「简洁、稳定」诉求不符。

目标：将内容存储真源切换为 **Markdown 文本 + md-editor-v3 编辑器**，现有数据**无缝迁移、不丢失内容**。

---

## 2. 产品目标（Product Goals）

| # | 目标 | 说明 |
|---|---|---|
| G1 | **存储语义现代化** | 内容真源由 HTML 富文本切换为 Markdown 纯文本，可 diff/版本化/长期可读、不被厂商绑定。 |
| G2 | **数据无缝迁移、零丢失、可回滚** | 现有数据零停机迁移，结构性内容 100% 不丢失；原 HTML 留备份，支持一键回滚；历史 Word 版本永久保留。 |
| G3 | **编辑体验平滑过渡** | 前端以 md-editor-v3 替换 wangEditor，保留自动保存/字数统计/判空等既有能力，用户无感切换。 |

> 三者正交：G1 解决"存什么"，G2 解决"怎么换不丢"，G3 解决"怎么用得顺"。

## 3. 用户故事（User Stories）

| # | 角色 | 故事 | 价值 |
|---|---|---|---|
| US1 | 内容编辑者 | 作为一个**内容编辑者**，我希望用 Markdown 编辑器（带实时预览）撰写项目内容，以便简洁地组织标题/列表/引用，而无需面对 Word 式工具栏噪音。 | 写作更聚焦、内容更干净。 |
| US2 | 归档检索者 | 作为一个**归档检索者**，我希望迁移后的内容保留全部标题/粗体/斜体/删除线/列表/引用/链接，以便检索与归档完整、无任何内容缺失。 | 检索结果不遗漏、可信。 |
| US3 | 运维 | 作为一个**运维人员**，我希望迁移零停机、有全量备份且可一键回滚，以便安全上线、出问题能快速恢复。 | 部署风险可控。 |
| US4 | 内容编辑者 | 作为一个**内容编辑者**，我希望保留 30s 自动保存草稿与字数统计，以便像现在一样不丢未保存内容。 | 编辑习惯延续。 |
| US5 | 归档检索者 | 作为一个**归档检索者**，我希望历史 Word 版本随时可下载/恢复，以便核对旧版式或审计。 | 历史可追溯。 |

## 4. 需求池（Requirements Pool）

优先级：**P0 = 必须，阻断上线；P1 = 重要；P2 = 可选增强**。

### P0 — 必须（阻断上线）

| ID | 需求 | 验收要点 |
|---|---|---|
| P0-1 | **全量在线备份**：迁移前调用现有 `Database.backup_to()` 做全量 SQLite 备份。 | 备份文件存在于 `data/backups/app_*.db` 且可还原。 |
| P0-2 | **双写过渡列 `content_format`**：`projects` 表新增列（默认 `'html'`），后端按 format 分发解析/导出，支持零停机过渡。 | 新旧内容按 format 正确渲染；迁移期间系统可读写。 |
| P0-3 | **幂等迁移脚本**：`scripts/migrate_html_to_md.py` 遍历 `content_format='html'` 项目，HTML→MD 转换，结构 100% 保留，按 `project_id` 定位、可重跑。 | 脚本重跑安全；结构无损。 |
| P0-4 | **往返校验**：每条迁移记录的 `md→纯文本` 与原 `html→纯文本` 必须一致（文本集合与顺序一致），差异为 0 才算通过。 | 全量校验通过率 100%。 |
| P0-5 | **原 HTML 可回滚**：原 HTML 保留为 `content_html_backup` 列或独立表，支持一键回滚。 | 任意 project 可还原至 HTML 真源。 |
| P0-6 | **历史 Word 版本永久保留**：`period_file_versions` BLOB 不参与改写，下载/恢复入口不变。 | 迁移前后 BLOB 条数一致，旧 docx 可下载/恢复。 |
| P0-7 | **标题层级映射一致**：保持现有约定 h1→H2、h2→H3、h3+→H4（与 `_RichTextParser` 一致）。 | 迁移后层级与现状一致。 |
| P0-8 | **前端换编辑器**：`ComposeView.vue` 用 md-editor-v3 替换 wangEditor，`form.content` 直接存 Markdown。 | 编辑器为 md-editor-v3，输出为 Markdown 字符串。 |
| P0-9 | **既有能力延续**：保留 30s 自动保存草稿、字数统计、判空（改用 md→纯文本提取）。 | 三大能力行为不变。 |
| P0-10 | **预览渲染**：项目详情/预览页引入 Markdown 渲染。 | Markdown 正确渲染。 |
| P0-11 | **Word 重生成读 Markdown**：`rebuild_period_word` 改为读取 Markdown 真源重新生成 docx，复用现有写出逻辑。 | 新 docx 文本内容与原 docx 一致（样式差异除外）。 |
| P0-12 | **依赖锁定**：引入 Markdown 库（迁移用 `markdownify`、导出用 `mistune`/`markdown`），版本锁定入 `requirements.txt`。 | 依赖可复现安装。 |

### P1 — 重要

| ID | 需求 | 说明 |
|---|---|---|
| P1-1 | **发布《迁移影响报告》**：统计「仅样式损失」条目（字体/字号/颜色/对齐）条数，供业务签字确认可接受。 | 作为上线放行依据。 |
| P1-2 | **受影响周期重建 Word**：对受影响周期重新 `rebuild_period_word`，使 docx 与新 MD 一致。 | 保证导出与真源一致（历史版本 BLOB 仍保留）。 |
| P1-3 | **禁用富样式粘贴**：新编辑器禁用富文本样式粘贴，防止再次引入噪音样式。 | 从源头控制。 |
| P1-4 | **灰度演练**：先让新内容走 MD，再跑全量迁移，质检样式损失项。 | 降低一次性风险。 |

### P2 — 可选增强

| ID | 需求 | 说明 |
|---|---|---|
| P2-1 | **颜色保留（若业务要求）**：采用「Markdown 正文 + 内联 HTML `<span style="color:">`」策略（GFM 允许原始 HTML）。 | 仅当业务坚持保留颜色时启用。 |
| P2-2 | **Cherry Markdown 备选集成**：仅当未来终用户强烈要求 Word 式所见即所得时实施（本次不实施）。 | 见已决议事项。 |
| P2-3 | **稳定后清理**：移除 HTML 解析分支与 `content_format` 旧值，保留报告与备份备审计。 | 上线稳定后择机执行。 |

## 5. UI 设计要点（UI Design Draft）

| 区域 | 设计要点 |
|---|---|
| **ComposeView 编辑器** | 改为 md-editor-v3 **分栏布局**：左侧 Markdown 编辑、右侧实时预览（默认开启）；暗黑模式跟随系统主题。 |
| **工具栏范围** | 仅保留迁移覆盖的能力：标题、粗体、斜体、删除线、有序/无序列表、引用、链接、撤销/重做。**移除**字体族、字号、文字颜色、段落对齐等工具栏项。 |
| **编辑习惯延续** | 30s 自动保存、字数统计、草稿恢复入口与现有一致，文案不变，用户无感。 |
| **预览/详情页** | 用 Markdown 渲染（md-editor-v3 预览或 `markdown-it`），排版清爽。 |
| **历史 Word 入口** | 现有「历史版本下载 / 恢复」入口（`/api/period-file-versions/.../download` 与 `/restore`）保持不变。 |

## 6. 已决议事项（Decisions，已与用户拍板）

1. **纯展示样式不保留**：字体族、字号、文字颜色、段落对齐 → 迁移时**丢弃**。理由：标准 Markdown 无语义等价物，对归档检索无价值；此为合理代价，**非内容丢失**。
2. **编辑器选型 = md-editor-v3**：Vue3 原生、集成成本最低、界面简洁、社区活跃、MIT 协议。**Cherry Markdown 仅作为**「若未来终用户强烈要求 Word 式所见即所得」时的备选，**本次不实施**。

## 7. 验收标准（Acceptance Criteria）

### 7.1 「无缝、不丢失内容」如何验证

| 维度 | 验收条件 |
|---|---|
| 备份存在 | 迁移前 `data/backups/app_*.db` 已生成且可还原。 |
| **往返校验通过率 100%** | 全量迁移记录 `md→纯文本` **等于** 原 `html→纯文本`（集合与顺序一致，差异计数 = 0）。 |
| 结构无损 | 抽样确认标题/粗体/斜体/删除线/列表/引用/链接在 Markdown 中表达正确。 |
| 样式损失已确认 | 《迁移影响报告》列出的「仅样式损失」条目经业务签字确认可接受。 |
| 可回滚 | 原 HTML 备份列存在；回滚脚本可将任意 project 还原至 HTML 真源。 |
| Word 历史不变 | `period_file_versions` BLOB 条数迁移前后一致，旧 docx 仍可下载/恢复。 |
| 零停机 | 迁移期间系统可读写，新旧内容按 `content_format` 正确分发渲染。 |
| 导出一致 | 基于 Markdown 重新生成的 docx 与迁移前 docx **文本内容一致**（样式差异除外）。 |
| 编辑器替换生效 | `ComposeView` 使用 md-editor-v3，自动保存/字数统计/判空功能正常。 |

### 7.2 上线放行门槛

- P0-1 ~ P0-12 **全部完成**；
- 往返校验通过率 100%；
- 《迁移影响报告》经业务确认；
- 回滚演练成功。

---

## 8. 范围边界（Out of Scope）

- 不做架构设计与编码（属架构师/研发职责）；
- 不保留纯展示样式（见已决议事项 1）；
- 不实施 Cherry Markdown（见已决议事项 2）；
- 不改动历史 Word 版本 BLOB 的存储与恢复机制。
