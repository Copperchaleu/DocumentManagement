## 评估：Word 富文本 → Markdown 迁移可行性（eval-markdown-migration）
- 需求（场景#15 日常开发）：评估将现有 Word 存储方案迁移为 Markdown，前端富文本编辑器替换为 Markdown 编辑器（候选 Vditor/Cherry/md-editor-v3/TOAST UI）。
- 关键源码实证：系统真源是 `projects.content`（wangEditor HTML TEXT），Word 仅是派生产物（`word_service.build_period_word_document` 把同周期项目 HTML 合并→docx BLOB `period_file_versions.file_content` + 本地 `data/documents/*.docx`）。故迁移=把 content 语义 HTML→MD，Word 可继续由内容重生成，无文件格式绑定。
- 兼容性结论：结构（标题/粗斜删/列表/引用/链接）100% 无损；字体/字号/颜色/对齐 标准 MD 无等价（纯展示样式，建议丢弃，必要时内联 HTML 保留颜色）。
- 数据兼容方案：全量备份(DB.backup_to) + 加 content_format 列双写过渡 + 幂等迁移脚本(markdownify HTML→MD) + 往返校验(md→纯文本 vs html→纯文本) + 原 HTML 备份列可回滚；历史 docx 版本 BLOB 永久保留。
- 后端改造：新增 MD→docx 解析（复用 _add_rich_content 写出层）、md_to_plain_text、引入 markdownify/mistune；需改 requirements.txt。
- 选型结论：首选 **md-editor-v3**（Vue3 原生、简洁、活跃、MIT，最契合栈）；备选 **Cherry Markdown**（腾讯，WYSIWYG 最接近 Word，非技术用户友好）；不推荐 TOAST UI（NHN 维护模式、仓库已移交 fork）、Vditor（过度复杂）。
- 交付：`docs/eval_markdown_migration.md`（详细评估全文）。未实现，仅评估。

## BugFix：导航栏分类树项目数量未聚合（software-bugfix-tree-count）
