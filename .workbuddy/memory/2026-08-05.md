## BugFix：项目内容编辑器工具栏按钮大量缺失（compose-editor-toolbar）
- 现象：切到 wangEditor default 模式后，工具栏只剩 headerSelect/字体/字号/粗体/斜体/下划线几个按钮，颜色/列表/引用/对齐/链接/撤销重做全部消失。
- 根因：上一步（compose-editor）工程师把删除线菜单 key 误写成 `'strikeThrough'`（非法 key；正确是 `'through'`，见 `@wangeditor/editor` dist 的 genSimpleToolbarKeys:23929 与 group-more-style）。wangEditor 工具栏遇到非法 key 会在该位置中断渲染，导致其后的所有按钮不显示——与现象完全吻合。
- 修复（software-bugfix-editor-toolbar，全 PASS）：web/src/views/ComposeView.vue toolbarKeys 中 `'strikeThrough'` → `'through'`；`editorMode` 保持 `'default'`（否则 fontFamily/fontSize 不注册，字体/字号功能丢）。
- 回归（QA 严过关）：逐 key 核对 18 个功能 key 全部为 wangEditor 5.1.23 合法注册 key；`strikeThrough` 残留 0；editorMode=='default'；后端 scripts/verify_font_export.py 复跑 11/11 PASS。
- 经验：wangEditor v5 的删除线菜单 key 是 `'through'`，不是 `'strikeThrough'`；显式 toolbarKeys 里含非法 key 会让工具栏渲染在该处中断。default 模式下 justify*/indent 等被包在 group-* 对象里，但作为独立 key 仍合法可渲染。

## BugFix：编辑页项目内容概率性丢失（compose-content-loss）
- 现象：项目列表点「编辑」跳到 `/compose?edit=<id>`，富文本内容有概率变空白，标题/分类不丢。
- 根因：wangEditor 的 `<Editor v-model="form.content">` 在自己的 `onMounted` 里 `createEditor({ html: props.modelValue })` 初始化，初始 html 渲染异步排队；而 `ComposeView` 原在父组件 `onMounted` 才通过 `loadEditPayload()` 填 `form.content`（晚于子组件挂载），导致异步空初始化偶尔覆盖事后 setHtml → 偶发空白。标题/分类走普通输入框不受影响。
- 修复（software-bugfix-compose-content-loss，QA PASS）：把表单加载从 `onMounted` 提前到 `setup` 阶段同步执行（`<Editor>` 挂载前 form.content 已就绪）；并在 `loadEditPayload` 内新增 `if (editorRef.value) editorRef.value.setHtml(form.content)` 防御运行时路由切换路径。
- 关键上下文：AppLayout.vue 用 `<keep-alive>` 包 router-view，ComposeView 只首次挂载一次，之后编辑导航走组件复用 + `watch(route.query)`；两路径修复均成立。
- 遗留（预存在，非本次回归）：`?edit` → 纯 `/compose` 时 `watch` 的 `([edit,create])` 两个分支都不命中，旧项目内容残留编辑区；页面有「重置表单」按钮可清空，建议后续在 watch 补 `else` 分支走 startNewProject。

## 评估：Word 富文本 → Markdown 迁移可行性（eval-markdown-migration）
- 需求（场景#15 日常开发）：评估将现有 Word 存储方案迁移为 Markdown，前端富文本编辑器替换为 Markdown 编辑器（候选 Vditor/Cherry/md-editor-v3/TOAST UI）。
- 关键源码实证：系统真源是 `projects.content`（wangEditor HTML TEXT），Word 仅是派生产物（`word_service.build_period_word_document` 把同周期项目 HTML 合并→docx BLOB `period_file_versions.file_content` + 本地 `data/documents/*.docx`）。故迁移=把 content 语义 HTML→MD，Word 可继续由内容重生成，无文件格式绑定。
- 兼容性结论：结构（标题/粗斜删/列表/引用/链接）100% 无损；字体/字号/颜色/对齐 标准 MD 无等价（纯展示样式，建议丢弃，必要时内联 HTML 保留颜色）。
- 数据兼容方案：全量备份(DB.backup_to) + 加 content_format 列双写过渡 + 幂等迁移脚本(markdownify HTML→MD) + 往返校验(md→纯文本 vs html→纯文本) + 原 HTML 备份列可回滚；历史 docx 版本 BLOB 永久保留。
- 后端改造：新增 MD→docx 解析（复用 _add_rich_content 写出层）、md_to_plain_text、引入 markdownify/mistune；需改 requirements.txt。
- 选型结论：首选 **md-editor-v3**（Vue3 原生、简洁、活跃、MIT，最契合栈）；备选 **Cherry Markdown**（腾讯，WYSIWYG 最接近 Word，非技术用户友好）；不推荐 TOAST UI（NHN 维护模式、仓库已移交 fork）、Vditor（过度复杂）。
- 交付：`docs/eval_markdown_migration.md`（详细评估全文）。未实现，仅评估。
